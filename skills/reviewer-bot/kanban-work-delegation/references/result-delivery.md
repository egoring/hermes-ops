# Getting results to the user without being asked

Use whenever a card, delegate_task, or cron produces a result the user is waiting on.

- **Standing user rule: results arrive before he asks.** When you promise "I'll post it when it lands", the promise is yours, not the wake system's. At every turn, first check each pending result's artifact (card status/comments, subagent output file, submission status) and post anything finished in your own words before answering the new message. A "아직 안됐어?" from the user means this check was skipped.
  - Scan **every** card you created or chained this session (`sqlite3 ... where created_at >= <session start>`), not only the card the new message is about. Chained cards (prep → notebook push → review) often finish while you are answering unrelated questions. A child card that auto-started and completed is just as much a pending result.
- **Diagnose a missed delivery by path before fixing anything:** (1) card → `notify-list <id>` (no subscription?); (2) delegate/watch → grep `not admitted` / `admission_conflict` in `logs/agent.log` from the completion time; (3) cron → `cron.scheduler: Job '<id>'` lines (`delivered to ... message_id=` proves it reached the chat; `empty stdout` means nothing was printed); (4) quiet hours → the hold file. Correct any earlier "it was missed" claim the logs disprove.

- **CLI `hermes kanban create` does NOT auto-subscribe** (only the `kanban_create` tool does; CLI is excluded on purpose). After every CLI create whose result the user waits on (fable final check, review, GPU), subscribe the thread in the shape that has actually delivered here: `hermes kanban --board <b> notify-subscribe <id> --platform discord --chat-id <thread> --thread-id <thread> --chat-type thread --parent-chat-id <channel> --guild-id <guild> --notifier-profile reviewer-bot --delivery-mode wake` (no `--user-id`). `wake` goes through session admission, so it also needs the admission fix below.
- **`notify-list` showing the row proves nothing; prove the subscription FIRES.** After the card's first event (claim, heartbeat, review request), its `last_event_id` in `~/.hermes/kanban/boards/<b>/kanban.db` table `kanban_notify_subs` must have moved past the value it had at creation. A row whose cursor still sits at its creation event is not being processed (seen with `--user-id` + `--delivery-mode notify` rows: no ping, no log line, for hours). Compare against a row on another board that did deliver (`gateway.run: kanban notifier: woke agent for <id>` in the gateway log) and copy its shape.
- **For a result the user is waiting on, keep one delivery path that is proven in this chat:** cron delivery with `deliver: origin` (the scheduler logs `delivered to discord:<thread> ... message_id=`). It does not depend on subscriptions or admission. Two shapes:
  - no_agent cron + a script that prints one line only when a watched item changes (submission watchers);
  - for kanban cards, an agent cron gated by `monitor=<script>`: the script prints a deterministic snapshot (e.g. `sqlite3 ~/.hermes/kanban/boards/<b>/kanban.db "select id,status,assignee,substr(title,1,60) from tasks where created_at >= <epoch> and status != 'archived' order by created_at"`, no timestamps), so the agent runs only when a status changes. Its prompt runs `kanban show` on the changed cards, posts 2–4 lines of verdict numbers, tags the user on review/blocked/final verdict outside quiet hours, outputs exactly `[SILENT]` on the first baseline tick, and never changes card state. Restrict it to the terminal toolset and set `workdir` to the project.
  After the first real status change, confirm the scheduler logged `delivered to discord:<thread>` before trusting it.
- **A watcher script that exits 0 on every parse failure is silently dead.** A CLI that starts printing an update warning before its CSV header made a `stdout.startswith("ref,")` check treat every tick as "transient failure", so score alerts stopped for days with only `empty stdout` in the scheduler log. Find the header offset instead of testing the first line, and keep a failure counter in the state file that prints one loud line after ~3 consecutive parse failures. After fixing, run the script once by hand: backlogged results print immediately, which also proves the fix.
- **Gateway restart preflight.** Kanban workers run as children of the gateway process (`ps -o ppid= -p <worker_pid>`), and the dispatcher docs say a restart can kill them. Before proposing a restart window, list running cards on EVERY board (`sqlite3 ~/.hermes/kanban/boards/<b>/kanban.db "select id,status,assignee,worker_pid from tasks where status in ('running','review') or worker_pid is not null"`). Name each one and how long it has run. The worst moment is a GPU card polling a pushed remote job: the kernel keeps running, but a respawned worker may redo the card. Recommend "restart when running = 0" and offer a cron that announces that moment; do not restart over live workers without the user weighing the loss.
- **Renamed Discord thread => every async wake (delegate_task completion, watch notices) is refused with `admission_conflict`, retried every minute forever.** Cause: `gateway/session_automation.py::_route_identity` compares display fields (chat_name, auto_thread_created, auto_thread_initial_name) of sessions.json `origin` (creation-time name) against the last committed human message source (current name). Diagnose: `grep "not admitted for discord chat=<thread>" logs/agent.log`. Local fix patch: `~/.hermes/local-patches/route_identity_display_fields.patch` (re-apply after `hermes update`). **An approved gateway patch does nothing until the gateway restarts**: when its review passes, tell the user in that same turn and ask for a restart window (a restart drops the live chat turn and running workers, so check that no card is running first). Until it is live, never trust delegate completion to arrive: poll the subagents' output files at your next turn and report proactively. If the user declines the restart, treat the cron watchers as the delivery path for good. Route result-bearing work through watched kanban cards instead of delegate_task. Do not ask again for a restart window: the patch applies on the next natural restart.
- Cron no_agent delivery (`deliver: origin`) uses the live adapter and is NOT affected by the admission bug.
- **A completion notice's `Result:` line is only the first line of the summary.** A checker summary that opens with a skill-usage line (`🧩 스킬: …`) therefore arrives with no content at all. Read the full summary with `hermes kanban show <id> --json` (the last run's summary) before replying. Relay a final check as a decision packet in your own words:
  1. what it verified
  2. what is still unverified, and the defects with their severity
  3. the checker's advice, then your own view
  4. numbered decisions for the user, recommended option first, each with its gain and its cost, e.g. "hold the submit until the rehearsal passes: +~3 h, removes a silent-ERROR risk"
  
  Fix the reviewer's own operational defects that it flags (watcher scripts, markers) in the same turn as the user's "추천대로".
- **A watcher reports only what it was told to watch.** A submission watcher keyed on a `watch` list in its state file never discovers new refs; every submit card (or queued-submit script) must append the new ref with a note, and the reply that announces the submit names the ref and confirms the watcher entry. When the user reports a score you did not post, check the watch list before blaming delivery.
- Before deleting a no_agent cron that uses `quiet_hours.emit`, check `cache/quiet_hold/<name>.jsonl`: held 23-09 messages flush only on that same job's next daytime run, so deleting the job strands them.
