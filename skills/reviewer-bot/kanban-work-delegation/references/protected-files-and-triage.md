# Protected instruction files and block-loop triage

## Editing AGENTS.md / SOUL.md / project .hermes config
These files are protected: every write needs a one-operation human approval, with no allowlist and no --yolo. The approval prompt goes to the session doing the write.

- **Do not route an AGENTS.md edit to a kanban worker by default.** A headless worker's prompt does not reach the user's chat, so it times out after 300s. The worker then correctly blocks (silence is not consent), and every retry burns another 5 minutes. This includes a docs card that also needs "one AGENTS line": split the card. Give the docs files to the worker, and apply the AGENTS sentences through route 1 in the same reply that the user approves.
- When you offer the user a choice of routes, spell out who types the edit in each option ("A: I apply it here with your approval" / "B: you edit it by hand"). Do not use a bare letter that an older commit message used for a different route, because the user picks by letter.
- Working routes, in order of preference:
  1. The user gives an explicit override ("edit it yourself"), and the Discord orchestrator session applies the exact pre-approved sentences with `patch`. The Discord gateway session either surfaces the approval inline or passes it. Commit only that file, then show the diff and line count.
  2. The user edits the file by hand from the card body.
  3. The user watches the desktop app while a worker retries. This is unreliable, so offer it last.
- Even with route 1, put the exact sentences in a card or spec first and change nothing else. The override covers that edit only; it does not lift the role boundary.

## Block loop → triage → auto-decomposition
- After about 2 blocks, a card goes to `triage`, and the auto-decomposer can split it into child cards within a minute. A comment saying "don't decompose" posted after the move is too late.
- Child cards run with fresh context and do not know why the parent blocked. One child completed the protected edit the parent could not, by an unverified path. After any triage move, run `hermes kanban show <id>` and look for a `decomposed {child_ids}` event. Audit each child's output before treating the parent as done.
- When the parent's blocker is a human gate (approval, credential, decision), resolve the gate with the user right after the **first** block, before the second block triggers triage.
- Never design a planned "stop here for reviewer check" gate as `kanban_block` on a card that has already blocked once: that second block sends it to triage. One such card got split into 3 children, which became its parents and pushed it back to `todo`. One child was dispatched at once and overwrote the reviewed scripts before it saw the stop comment. For a pre-launch check, have the worker post the diff and smoke results as a comment, then `kanban_schedule` with a short wake time. Or count blocks first (`show --json` events) and use the gate only on the first block.
- A card that waits on an external queue (TPU or GPU kernel, scoring) must not block when it hits its wait limit. Write "comment, then `kanban_schedule` to the next check" into the card, so the decision goes to the reviewer without starting a block count. When the auto-decomposer splits such a card, the children rebuild the whole procedure, including a "push once" step. A second push is an irreversible quota spend, so archive every unstarted child at once, then comment the decision on the parent.
- Clean up after a split. Unlink each child→parent edge (`unlink <child> <parent>`); the parent becomes `ready` again. Archive the children that have not started. Comment on any running child so it completes as a no-op. Then check the parent's files with md5 against the copy that was actually tested, because children can write to the shared workspace.
- After a triage split, completion notices for the children and the parent keep arriving out of order, often after the parent is already approved. Check each one against the board (`show <id>`: status, commit in result). If the work is already merged, reply in 2–3 lines (which commit carries it, nothing to do) and take no action. Do not re-review the work or create a follow-up card.
- Gap-filling a protected edit through route 1 after children have run: patch only the missing line, `git diff --stat` must show +1, and commit it separately with the user decision named in the message.
- A worker that blocked on the approval prompt can leave the hunks it wrote before the prompt applied but uncommitted. Read `git diff <file>` and check each hunk against the spec. Add only the missing sentence, commit the file alone (state the route and the user decision in the message), then unblock and complete the card yourself. Do not let the worker retry, because a retry would rewrite hunks that are already correct.
- A `scheduled` card cannot be completed; `complete` fails. Use `archive` to close a scheduled card whose work is cancelled. `unblock` would make it claimable, and a worker could start it.
